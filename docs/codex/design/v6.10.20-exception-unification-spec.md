> **Version**: v6.10.20

> **Status**: Shipped

> **Tests**: `tests/test_v61020_exceptions.py`

---

## 1. 设计目标

当前代码库中有 75% 的 `try` 块使用裸 `except Exception:`，导致：

- 调试时无法从异常类型直接判断故障层级（Agent / DB / LLM / API）。
- 可能意外吞掉 `KeyboardInterrupt`、`SystemExit`（虽然当前 bare `except:` 数量为 0，但 `except Exception` 仍有此风险）。
- API 错误响应格式由各路由自行拼装，缺乏一致性。

本版本的目标是在**不改动现有 `except Exception:` 代码**的前提下，建立分层异常体系，并在新增/重构代码中优先使用统一类型。

---

## 2. 核心设计原则

1. **向后兼容** — 所有新类型均继承 `Exception`，因此现有 `except Exception:` 仍可捕获它们，无需批量修改旧代码。
2. **分层语义** — 每种异常对应一个清晰的架构层级（Agent / DB / LLM / API），调用方可按需捕获特定类型。
3. **渐进迁移** — 只在**新增代码或试点模块**中引入新类型，不改现有异常处理逻辑，避免回归风险。
4. **最小侵入** — 不引入外部依赖；纯标准库实现。

---

## 3. 异常类型定义

### 3.1 类型总览

| 类型 | 继承 | 抛出层级 | 典型场景 |
|------|------|---------|---------|
| `AgentExecutionError` | `Exception` | `agent_runtime/` / `agents/` | Agent 执行某一步失败（如 LLM 调用、输出校验） |
| `DBTransactionError` | `Exception` | `db/repositories/` | SQLite 约束失败、超时、事务回滚 |
| `APIValidationError` | `Exception` | `api/routes/` | 请求参数缺失、JSON 非法、业务规则校验失败 |
| `LLMProviderError` | `Exception` | `llm/` | 远程模型 429、超时、响应格式错误 |

### 3.2 详细定义

#### `AgentExecutionError`

```python
class AgentExecutionError(Exception):
    def __init__(self, agent: str, step: str, error: Exception) -> None:
        self.agent = agent      # e.g. "author", "editor"
        self.step = step        # e.g. "invoke_llm", "validate_output"
        self.error = error      # 原始异常
        super().__init__(f"[{agent}] {step} failed: {error}")
```

- 由 Agent 基类或具体 Agent 在步骤失败时抛出。
- 携带 `agent` + `step` + 原始异常，便于上层（如 workflow runner）记录结构化日志。
- 当前试点：`novel_factory/agent_runtime/base.py`。

#### `DBTransactionError`

```python
class DBTransactionError(Exception):
    pass
```

- 由 Repository 层在 `sqlite3.Error` 或事务边界失败时抛出。
- 保持极简（无额外字段），因为 SQLite 的错误信息本身已足够（约束名、SQL 语句）。
- 当前试点：计划 deferred 到 v6.10.21+，但在 v6.10.20 的 Phase B 试点中已在 `db/repositories/` 的 7 个文件（`auto_run`, `batch`, `memory_update`, `queue`, `serial`, `story_fact`, `style_bible`）中引入 `sqlite3.Error` → `DBTransactionError` 的包装。

#### `APIValidationError`

```python
class APIValidationError(Exception):
    def __init__(self, code: str, message: str) -> None:
        self.code = code        # e.g. "VALIDATION_ERROR", "NO_RUNS_SELECTED"
        self.message = message  # 人类可读描述
        super().__init__(message)
```

- 由 API 路由在 FastAPI 依赖校验之外的业务校验中抛出（如批量操作前的前置检查）。
- 提供 `code` 字段便于前端做 i18n 或错误分类。
- 当前试点：`api/routes/runs.py`, `production.py`, `genesis.py`, `projects.py`, `chapter_readonly.py`, `chapter_briefs.py`（6 个文件）。

#### `LLMProviderError`

```python
class LLMProviderError(Exception):
    pass
```

- 由 LLM Provider 层在远程调用失败、重试耗尽、响应无法解析时抛出。
- 当前试点：计划 deferred 到 v6.10.21+，但在 `llm/openai_compatible.py` 中已引入 `openai.APIError` / `httpx` 超时 → `LLMProviderError` 的包装。

## 4. 试点策略与选择理由

### 4.1 试点范围

| 模块 | 引入类型 | 风险等级 | 理由 |
|------|---------|---------|------|
| `agent_runtime/base.py` | `AgentExecutionError` | 低 | 底层基础设施，不直接暴露 API；Agent 执行异常是高频调试场景 |
| `api/routes/runs.py` | `APIValidationError` | 中 | 高频路由，错误响应格式统一收益最大；但影响面最广，需全量测试验证 |
| `api/routes/production.py` | `APIValidationError` | 中 | 生产自动化入口，前置校验多 |
| `api/routes/genesis.py` | `APIValidationError` | 中 | 创世流程入口，参数校验复杂 |
| `api/routes/projects.py` | `APIValidationError` | 中 | 项目 CRUD 入口 |
| `api/routes/chapter_readonly.py` | `APIValidationError` | 低 | 只读路由，校验简单 |
| `api/routes/chapter_briefs.py` | `APIValidationError` | 低 | Brief 相关路由，校验简单 |

### 4.2 为什么从 `agent_runtime/base.py` 开始

1. **风险最低**：不直接面向 HTTP 客户端，即使引入异常失败也只在内部 workflow 层暴露。
2. **收益明确**：Agent 执行失败是最常见的调试场景，统一异常类型可让 runner 做结构化日志。
3. **可扩展性**：试点成功后，自然向上推广到 `agents/` 和 `api/`。

### 4.3 为什么 API 路由扩展到 6 个文件

初始计划只试点 `runs.py`，但在 Phase B 中发现 `production.py`、`genesis.py`、`projects.py` 等路由的前置校验逻辑（如 `NO_RUNS_SELECTED`、`INVALID_PROJECT_ID`）具有相同的模式，因此将 `APIValidationError` 统一推广到所有包含自定义校验的路由文件。

## 5. 与现有代码的兼容性

### 5.1 继承关系

```
Exception
├── AgentExecutionError
├── DBTransactionError
├── APIValidationError
└── LLMProviderError
```

所有类型均直接继承 `Exception`，因此：

```python
# 现有代码继续工作
try:
    raise AgentExecutionError("author", "invoke_llm", RuntimeError("timeout"))
except Exception as e:
    # 可捕获
    pass
```

### 5.2 增量升级路径

旧代码无需改动。新代码可按需使用更精确的捕获：

```python
# 新代码：精确捕获
try:
    result = await agent.invoke(step="draft")
except AgentExecutionError as e:
    logger.error(f"Agent {e.agent} failed at {e.step}: {e.error}")
except DBTransactionError as e:
    metrics.inc("db_error")
    raise
```

## 6. 异常编码规范

### 6.1 `APIValidationError` 的 `code` 命名规范

- 使用大写蛇形命名：`VALIDATION_ERROR`、`NO_RUNS_SELECTED`、`PROJECT_NOT_FOUND`
- 禁止在 `code` 中放动态值（如 `PROJECT_NOT_FOUND_demo`），动态值应放在 `message` 中
- 每个路由文件应维护自己的 code 列表，并在 docstring 中注释

### 6.2 `AgentExecutionError` 的 `agent` / `step` 命名规范

- `agent`：使用小写模块名（`planner`, `screenwriter`, `author`, `polisher`, `editor`）
- `step`：使用动作名（`invoke_llm`, `validate_output`, `parse_json`, `check_continuity`）
- 同一 Agent 的多个步骤应共享 `agent` 值，不同 `step` 值

## 7. 测试策略

### 7.1 测试文件

`tests/test_v61020_exceptions.py` — 13 个测试用例，覆盖：

- 基本属性验证（`agent`/`step`/`error` 或 `code`/`message`）
- 被 `except Exception:` 捕获（向后兼容）
- 被特定类型捕获（分层语义）
- `__repr__` 往返一致性
- 四种类型统一被 `tuple` 捕获
- 继承关系验证（`issubclass(X, Exception)`）

### 7.2 回归验证

全量测试：3,768 个用例通过，0 失败。新增异常类型不破坏任何现有测试。

## 8. 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 试点模块引入回归 | 低 | 中 | 不改现有 `except Exception`；只在新代码中使用；全量测试验证 |
| 开发者不理解分层语义 | 中 | 低 | 本文档提供编码规范；代码审查强制执行 |
| 与现有异常处理冲突 | 低 | 中 | 新类型继承 `Exception`，现有 `except Exception` 仍可捕获 |
| 过度推广导致失控 | 中 | 中 | Phase B 严格限制在 6 个 API 路由文件；`db/` 和 `llm/` 的 deferred 项在后续版本按需执行 |
