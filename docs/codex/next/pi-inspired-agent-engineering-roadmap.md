# Pi-Inspired Agent Engineering Roadmap

## Purpose

This document translates useful ideas from `earendil-works/pi` into Novelos' next Agent engineering direction.

It is not an integration plan for the Pi codebase. Novelos should not replace its Python/FastAPI/LangGraph production chain with Pi. The goal is to borrow the right product and engineering primitives:

- context engineering,
- skills and prompt templates,
- session history and branching,
- observable event streams,
- provider abstraction,
- extensible Agent harness boundaries.

## External Reference

Reference project:

```text
https://github.com/earendil-works/pi
https://pi.dev/
```

Observed Pi concepts relevant to Novelos:

1. Minimal but extensible Agent harness.
2. Project instructions via `AGENTS.md` and prompt customization.
3. Skills loaded on demand with progressive disclosure.
4. Prompt templates as reusable commands.
5. Dynamic context injection and customizable compaction.
6. Tree-structured session history with branch/share/export.
7. JSON/RPC/SDK execution modes.
8. Multi-provider LLM abstraction.
9. Event-oriented terminal/web UI surfaces.

## Product Fit For Novelos

Novelos is not a coding agent. It is a personal long-form authoring workbench.

The right interpretation is:

```text
Pi-style Agent harness ideas -> Novelos writing Agent runtime
```

Do not interpret this as:

```text
Install Pi and replace Novelos agents
```

Novelos should keep:

- FastAPI backend,
- SQLite project store,
- React Author Workbench,
- LangGraph chapter workflow,
- existing `planner -> screenwriter -> author -> polisher -> editor -> publisher` chain.

Novelos should improve:

- how Agent context is selected,
- how skills are discovered and invoked,
- how runs are observed and replayed,
- how generated alternatives are versioned and branched,
- how model/provider selection is configured and explained.

### v5.8: Workflow Observability And Recovery

Pi influence: event streams, session timeline, steerable execution, shareable history.

Goal:

Make every chapter run inspectable while it is running and understandable after it finishes.

Status: completed in `docs/codex/planning/novel-factory-v5.8-workflow-observability-recovery-spec.md`.

Scope:

1. Persist node-level run logs:
   - node name,
   - started/finished timestamps,
   - status,
   - input summary,
   - output summary,
   - error summary,
   - token/latency/cost when available.
2. Expose workflow timeline API:
   - latest run detail,
   - node events,
   - artifacts generated by each node,
   - recovery recommendation.
3. Upgrade workflow UI:
   - live node log stream,
   - human-readable node status,
   - stale-run explanation,
   - retry/reset boundary shown clearly.
4. Keep recovery bounded:
   - no blind rerun over terminal chapters,
   - no overwrite of planned chapters with existing content,
   - clear "resume/retry/reset" semantics.

Non-goals:

- no full replay engine yet,
- no sub-agent orchestration rewrite,
- no replacement of LangGraph.

Acceptance:

1. A running chapter shows live node progress and recent log messages.
2. A completed chapter shows a readable timeline from planner to archive.
3. A failed/stale run shows where it stopped and what recovery action is safe.
4. Existing v5.5.15/v5.6.1/v5.7 guards still pass.
5. `python3 scripts/verify.py full` passes before declaring baseline.

### v5.9: Writing Skills And Prompt Template System

Pi influence: skills, prompt templates, extensions as composable capability packages.

Goal:

Turn hard-coded writing improvements into discoverable, reusable author skills.

Candidate skills:

- Foreshadowing check,
- Character voice consistency,
- Scene tension enhancer,
- Web-novel hook enhancer,
- AI-trace reducer,
- Continuity check,
- Local polish,
- Chapter recap generator,
- Title/synopsis generator,
- Plot-hole resolver.

Scope:

1. Define a Novelos writing skill manifest:
   - id,
   - name,
   - description,
   - applicable surfaces,
   - required inputs,
   - output schema,
   - risk level,
   - model profile hint.
2. Add backend skill registry for writing actions.
3. Add skill execution API:
   - selected chapter/paragraph,
   - instruction,
   - skill id,
   - structured result.
4. Add Author Workbench skill launcher:
   - selected text,
   - available actions,
   - preview result,
   - accept/reject/save version.
5. Store skill results in version metadata and/or artifacts.

Non-goals:

- no arbitrary remote code execution,
- no marketplace,
- no multi-user permission system.

Acceptance:

1. At least 3 writing skills are available in the editor.
2. Skill outputs are structured and previewed before modifying text.
3. Accepted skill output creates a readable version entry.
4. Skill prompts are stored as templates, not scattered strings.
5. Tests cover registry, API, and editor interaction.

### v6.0: Longform Context Engineering And Memory Governance

Pi influence: dynamic context, compaction, project instructions, session trees.

Goal:

Make long-form generation more consistent by explicitly managing what enters the model context.

Scope:

1. Context package builder:
   - project premise,
   - world facts,
   - character state,
   - active plot threads,
   - unresolved foreshadowing,
   - chapter instruction,
   - recent chapter summaries.
2. Context budget policy:
   - required context,
   - optional context,
   - fallback compression,
   - token budget preview.
3. Memory review workflow:
   - extracted facts,
   - suggested updates,
   - conflicts,
   - accept/edit/ignore.
4. Chapter summary compaction:
   - chapter-level summaries,
   - arc-level summaries,
   - character delta summaries.
5. Context audit UI:
   - what was injected,
   - why it was injected,
   - what was omitted.

Non-goals:

- no broad enterprise RAG platform,
- no external vector system unless necessary,
- no hidden automatic memory overwrite without human review.

Acceptance:

1. Each Agent run can show a context manifest.
2. Context size and token budget are visible.
3. Long projects use summaries instead of raw full-history stuffing.
4. Memory conflicts are visible before application.
5. Generation quality improves through traceable context decisions, not opaque prompt growth.

## Implementation Principles

1. Borrow primitives, not code.
2. Keep changes narrow and author-facing.
3. Every AI mutation must be previewable or reversible.
4. Every run should be inspectable.
5. Every context decision should be explainable.
6. Avoid enterprise scope until personal authoring feels strong.

## What Not To Do

Do not:

- replace LangGraph with Pi,
- port the backend to TypeScript,
- add Pi as a runtime dependency just for inspiration,
- add multi-tenant/RBAC as part of this line,
- build a generic Agent platform before improving the authoring loop,
- expose raw internal keys as user-facing labels.
